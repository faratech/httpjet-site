Running it

Operations & deployment

httpjet is designed for a conventional Linux service deployment: a dedicated account, the LiteSpeed-compatible configuration tree, systemd socket activation, and an explicit separation between the web tier and a persistent PHP pool. The checked-in units are generic references, not a copy of any live environment.

Installation status

Public signed binary packages and an installer are not published yet. Today, build from source and follow the included systemd reference. Do not treat internal build, benchmark, or deployment scripts as a public installation path.

source install · a configuration tree
cargo build --release -p httpjet
sudo useradd --system --home-dir /var/lib/httpjet --no-create-home \
  --shell /usr/sbin/nologin httpjet
sudo install -m0755 target/release/httpjet /usr/local/httpjet/bin/httpjet

# the server root: an existing LiteSpeed tree works as-is
sudo /usr/local/httpjet/bin/httpjet --root /usr/local/lsws check --strict

sudo cp packaging/systemd/httpjet-example.service /etc/systemd/system/httpjet.service
sudo systemctl daemon-reload
sudo systemctl enable --now httpjet
!
Review before start

The example units and example configuration bind loopback and use example document roots. Set the listener, domains, document roots, TLS material, and writable application paths deliberately before enabling a public service.

Systemd model

The reference deployment splits into four units:

UnitRole
httpjet.socketOwns the listening sockets: ReusePort=yes TCP :80 / :443 (and :443 UDP for HTTP/3), backlog 8192. The fd count must match serve --workers.
httpjet-boot-ready.serviceA boot gate that blocks the web tier until the configuration and backends are actually available (availability-first, bounded timeout).
httpjet.serviceThe web tier: httpjet --root /usr/local/lsws serve --lsphp-external … under a dedicated account, OOMScoreAdjust=-500, LimitNOFILE=1048576.
httpjet-lsphp.socket + httpjet-lsphp.serviceThe persistent LSAPI pool under its own identity, Type=notify; reload replaces the worker generation without closing the systemd-owned listener.

Socket activation is a deploy property, not an optimization: because the manager owns the listening sockets, a binary deploy never refuses new or queued connections — new sockets accept immediately while old workers drain under TimeoutStopSec. The reference drop-ins also run a root ExecStartPre permission script and then drop to the unprivileged service account; conflicts are declared against lshttpd.service, so a LiteSpeed and httpjet cannot run simultaneously.

Safe change workflow

  1. Edit the configuration tree or application content in a reviewable change.
  2. Run httpjet --root … check --strict — the deploy gate: topology lint, docroot checks, and inert-config warnings (geo lists without a db, auth without Require, wildcard PROXY-protocol binds). SIGHUP with a broken config keeps the old generation, but the check should catch it first.
  3. Test with isolated listeners, a separate PHP socket, and a separate page-cache store path.
  4. Restart through systemd for listener, TLS-binding, PHP-pool, or binary changes; systemctl reload replaces configuration in-place where safe.
  5. Probe the origin directly and check service logs; purge any outer cache if an incorrect cacheable response reached it.

Keep installed binaries outside Cargo's target/ directory. A source build or cargo clean must never remove the binary a running unit depends on.

The persistent PHP pool

Static and reverse-proxy deployments need no PHP. For LSAPI, the supplied httpjet-lsphp.socket and httpjet-lsphp.service units run a persistent pool (httpjet lsphp) under the httpjet-php account; the web tier dials it with serve --lsphp-external <socket> plus the shared --lsphp-generation-file. This lets the web service restart without cold-starting PHP, and an opcache recycle (httpjet lsphp-reload or a pool restart) replaces worker generations without dropping the listener. See LSAPI & PHP for the wiring and the generation-file trust rules.

Cache safety and observability

The page cache is off by default. Before enabling it, prove the application has explicit cache headers and exercise URL, host, scheme, cookie/private-tier, and purge behavior for that application. A cache bug may be retained by an outer CDN after the origin is repaired.

observability · metrics, headers, purge
# Prometheus metrics on the configured, normally loopback-only address
curl -s http://127.0.0.1:9090/metrics | grep '^httpjet_'

# cache state and budgets (locally throttled debug render)
curl -s http://127.0.0.1:9090/cache-entries

# the cache status header
curl -I -H 'Host: example.test' http://127.0.0.1:8080/ | grep -i x-litespeed-cache

# loopback tag purge
curl -s -X POST -H 'x-litespeed-purge: example' \
  -o /dev/null -w '%{http_code}\n' http://127.0.0.1/__hj_cache_purge

/cache-entries reports hits, misses, stores, purges, file-tier errors, and byte budgets; the Prometheus httpjet_* family covers requests, phases (including proxy upstream latency), throttle and failover counters, TLS handshakes (full vs resumed), fast-memo hits, and cache activity. A telemetry TSV, a PHP slow-log, and an opt-in pprof endpoint (--profile-token, --features profiling) round out the tooling. Judge cache health by the counters and direct content checks, not a transient raw file count.

Logging defaults: access and error logs roll at 50 MB with 30-day pruning, per-vhost logs are configurable in the XML, the access log can emit JSON (HTTPJET_ACCESS_LOG_FORMAT=json), and every rendered line can mirror to syslog (HTTPJET_SYSLOG_TARGET) without touching the request path.

Release and upgrade discipline

A public release must provide portable x86_64 and aarch64 artifacts, checksums, signatures or attestations, an SBOM, a license, and a documented Linux/kernel/libc support floor. Existing architecture-tuned PGO helpers are deployment-specific and must not be uploaded as generic binaries.

Package upgrades should preserve the configuration tree, dictionaries, and state; stage and validate a new binary before restart; and retain a known-good binary for rollback. Dictionary rotation is deliberate: write the new file atomically, validate its configuration, restart the service, and expect old dictionary-generation cache entries to become safe misses.
