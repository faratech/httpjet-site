Running it

Operations & deployment

httpjet runs in production as an active-active pair on :80/:443 — one x86-64 node, one aarch64 node — pulled by Cloudflare over mutual TLS. It is supervised by systemd and watched by monit, deployed one node at a time as a PGO binary, and gated by a battery of cache-correctness scripts that must pass before the edge is trusted. This page is the runbook: topology, the deploy flow, the gates, and the build & test commands.

Production topology

Two nodes serve the live edge: an x86-64 host and an aarch64 host, both bound to :80 and :443, both pulled by Cloudflare. Either can carry the whole site, so a deploy that touches one node at a time always leaves Cloudflare a live origin to fall back to. There is no LiteSpeed serving anymore — httpjet is the edge, and the only serving transport is pure io_uring / monoio.

Active-active pair · x86-64 + aarch64 :80 / :443 behind Cloudflare httpjet.socket activation systemd · Restart=always monit-watched · self-heals in ~2 s drops to nobody:nobody

Each node uses three systemd units: httpjet.socket owns the public listener fds, httpjet.service inherits them and serves the web tier, and httpjet-lsphp.service keeps the external PHP pool warm. The service has Restart=always, runs with --page-cache, and is additionally watched by monit, so a stray kill self-heals in roughly two seconds. The unit runs the stable binary, deliberately not the build output under target/:

unit · the stable binary path
# /etc/systemd/system/httpjet.service (sketch; fds from httpjet.socket)
ExecStart=/usr/local/httpjet/bin/httpjet --root /usr/local/lsws serve --page-cache …
Restart=always
User=nobody
Group=nobody

The unit points at /usr/local/httpjet/bin/httpjet — a stable install path that survives a cargo clean, unlike target/release/httpjet. The process drops privileges to nobody:nobody. Start, stop, and restore are always done through systemd (systemctl {start,restart,stop} httpjet): a plain kill just gets respawned, so taking the edge down for maintenance means an actual systemctl stop. Socket activation keeps the listener fds open across a web-tier restart; accepted in-flight requests still have to drain within the normal shutdown window.

Configuration

httpjet reads the same LiteSpeed configuration it was built to replace — /usr/local/lsws/conf/httpd_config.xml plus the per-vhost files under vhosts/*.xml. That tree is read-only; httpjet never writes to it. The same XML drives the same virtual hosts, listeners, contexts, and .htaccess behavior.

Before serving anything, the config can be linted without binding a single port — this is the first thing the deploy script runs, and the right way to sanity-check an edit:

check · lint without binding ports
$ httpjet --root /usr/local/lsws check

# strict mode — the form the deploy script gates on
$ httpjet --root /usr/local/lsws check --strict
i
Read-only by design

Both /usr/local/lsws and the config tree are read-only. httpjet treats the LiteSpeed XML as ground truth and parses it through hj-config ($VAR substitution, listener/vhost resolution). A config mistake is caught at check time, not at the listener.

Zero-downtime PHP

The lsphp pool is its own systemd unit — httpjet-lsphp.service — and the web tier dials it over a Unix socket rather than spawning PHP itself. The server connects with serve --lsphp-external, so restarting the web tier never cold-starts the PHP pool:

serve · external lsphp pool
# the PHP pool is a separate, long-lived unit
$ systemctl status httpjet-lsphp

# the web tier dials it — no spawn, no opcache cold-start on restart
ExecStart=… serve --lsphp-external /tmp/php8-httpjet-c1.sock --page-cache

The payoff: systemctl restart httpjet redeploys a fresh server binary with zero PHP downtime — the warm lsphp children, with their primed opcache, stay up across the restart. (Forcing an opcache recycle is a deliberate, separate systemctl restart httpjet-lsphp.) The full PHP path is covered in LSAPI & PHP.

The deploy flow

Deploys are PGO, per-architecture, and strictly one node at a time. A PGO profile is gathered by running the instrumented binary on its own architecture, so the binaries cannot be cross-compiled — the aarch64 build runs natively on the ARM node. The shape of a deploy is build → install → restart → gate, repeated per node:

StepWhat happens
buildscripts/build-pgo.sh produces the PGO binary. Run on the x86-64 node for x86-64, and natively on the aarch64 node for aarch64 — the profile is architecture-specific.
preflightscripts/deploy-lscache.sh runs check --strict (config lint), a self-peer guard (the cache peer must be the other node, never itself), and a co-listener guard (nothing else may be sharing the port).
installThe fresh build is installed into bin/ (the previous binary is kept as bin/httpjet.prev) and the unit is restarted with systemctl restart httpjet.
health-checkThe deploy script probes the loopback origin. On failure it auto-reverts to bin/httpjet.prev and restarts — the previous-good binary is one restart away at all times.
soak & gateRun the cache-correctness gates against the just-deployed node, soak the first node, then repeat the whole flow on the second.
deploy · PGO build → install → restart
# 1) build the PGO binary on this architecture
$ scripts/build-pgo.sh

# 2) install into bin/ + systemctl restart httpjet
#    runs check --strict, self-peer guard, co-listener guard,
#    then health-checks loopback and auto-reverts on failure
$ bash scripts/deploy-lscache.sh

Deploying one node at a time is the load-bearing rule: while the first node is restarting (or rolling back), the second is still serving Cloudflare, so the edge never loses an origin. Soak the first node before touching the second.

There is no --io-uring flag and no URING=0 environment rollback. The io_uring transport is the normal binary. If a transport-level regression ever requires backing out, rollback means reinstalling the previous-good binary or rebuilding from the previous revision.

i
R&D never touches the live edge

Anything that isn't a deploy — benchmarking, reproducing a bug, kicking the tires — runs on alternate ports with a separate --php-socket and a low --php-children, never the production :80/:443 or the prod PHP socket. A leaked alt-port instance silently shares the port via SO_REUSEPORT with its own cache and .htaccess state, so test instances are cleaned up by exact PID and the port is verified clear afterward.

Cache-correctness gates

The page cache is the one subsystem that can serve wrong content if a key or isolation rule is broken, so a deploy is not trusted until four regression scripts and a purge smoke all pass. Each targets one historically real failure class:

GateWhat it catches
cache_xurl_test.shFront-controller cache poisoning — three distinct URLs must each keep their own content (XenForo rewrites every page to /index.php, so a key-by-resolved-path bug would collapse the whole site to one entry).
cache_scheme_test.shThe cross-scheme redirect loop — an HTTP :80 hit must not poison the HTTPS entry with an origin canonical 301 that replays to HTTPS clients as a redirect loop.
cache_xhost_test.shForeign-host isolation — a request for an unmapped host must not be served content built for another vhost.
cache_private_test.shPrivate-tier session isolation — a logged-in (per-session) entry must never cross into the public entries, in either direction.
gate · run before trusting the edge
# front-controller cache-poisoning (three distinct URLs)
$ HJ=127.0.0.1:443 HOST=windowsforum.com bash scripts/cache_xurl_test.sh / /whats-new/ /help/

# cross-scheme HTTP→HTTPS redirect loop
$ HJ_HTTP=127.0.0.1:80 HJ_HTTPS=127.0.0.1:443 HOST=windowsforum.com bash scripts/cache_scheme_test.sh /

# foreign-host isolation + private-tier session isolation
$ HJ=127.0.0.1:443 HOST=windowsforum.com bash scripts/cache_xhost_test.sh /
$ HJ=127.0.0.1:443 HOST=windowsforum.com bash scripts/cache_private_test.sh /help/

# purge smoke — must return 204
$ curl -s -X POST -H 'x-litespeed-purge: tag=__deploy_smoke' \
    -o /dev/null -w '%{http_code}\n' http://127.0.0.1/__hj_cache_purge

The full mechanics of the cache — keying, the identity guard, the purge protocol — live in Page cache. The gates exist because the worst-case blast radius of a cache bug is wide, which is the subject of the next section.

The Cloudflare coupling

Cloudflare sits in front of both nodes, and that changes the cost of a cache mistake. A wrong cached response doesn't just live in the origin cache — Cloudflare edge-caches it too, for the response's own max-age. Some permalinks carry a multi-day edge TTL.

!
A cache bug can outlive a rollback

Because Cloudflare pins a wrong response at its edge for up to a 7-day TTL on some permalinks, rolling the origin binary back does not fix what is already cached upstream. A bad cache requires two actions: fix the origin and purge Cloudflare. This is exactly why the cache-correctness gates are mandatory before a deploy — catching the bug at the origin is far cheaper than chasing it across the edge.

So the remediation order for a cache incident is: confirm the origin is now correct over loopback (curl -sk -H 'Host: …' https://127.0.0.1/<path>), then purge Cloudflare for the affected zone — a rollback alone is not enough.

Observability

The cache exposes its internals on a loopback-only metrics listener — --metrics-addr, default 127.0.0.1:9090. It is never reachable from the public listeners, so introspection can't leak. The key endpoint is /cache-entries:

observe · the metrics listener
# entries/bytes, per-URL-class counts, hits/misses/stores/purges + error counters
$ curl -s http://127.0.0.1:9090/cache-entries

# the per-response verdict — hit / miss — is on the wire
$ curl -skI -H 'Host: windowsforum.com' https://127.0.0.1/help/ | grep -i cache
X-LiteSpeed-Cache: hit

Three signals together tell the operational story:

  • /cache-entries — total entries and bytes, per-URL-class counts, and the health line of hits/misses/stores/purges plus error counters.
  • The X-LiteSpeed-Cache header — hit when the cache served the response, miss when it ran but stored instead, absent when the response wasn't cacheable.
  • Access & error logs — non-blocking, and they record the real wire bytes and the real client IP (resolved from the X-Forwarded-For chain behind the trusted Cloudflare proxy, not the edge IP).
⎁
In production

The production unit keeps the default loopback metrics listener at 127.0.0.1:9090. It is not exposed on public listeners; disable it with an empty --metrics-addr only when local introspection is intentionally unavailable.

loopback-only listener · default 127.0.0.1:9090

The cache kill switch

If the page cache itself needs to be taken out of the loop — without reverting a binary — drop --page-cache from the unit and restart. The cache code is inert without the flag: the lookup and store seams become a near-free pass-through, and every request goes straight to its backend.

kill switch · disable the cache only
# drop --page-cache from ExecStart (override or edit the unit), then:
$ systemctl restart httpjet
# the cache is now bypassed entirely; the rest of the server is unchanged

Build & test

The local development and CI commands. Builds come in two flavors: a fast release build for everyday work, and the PGO build used for production and for any benchmark that's meant to be believed. Both builds use the same pure io_uring transport; transport rollback is a source/binary rollback, not a build flag.

build · release vs PGO
# release: LTO thin + codegen-units=1 (slow link, fast binary)
$ cargo build --release

# the production build — profile-guided optimization
$ scripts/build-pgo.sh
test · full suite to one file
# the full suite — ~1,050 tests across the 15 crates
$ cargo test

# one crate
$ cargo test -p hj-rewrite

# one integration-test file
$ cargo test -p hj-rewrite --test redirect_repro

# live tests (#[ignore]): spawn lsphp, read certs — run separately
$ cargo test -- --ignored
inspect · lint the config
$ ./target/debug/httpjet --root /usr/local/lsws check

For local serving, the rule from the deploy section applies in full: never bind the production ports or socket. A development instance takes alternate ports and its own PHP socket so the live edge is untouched —

serve · R&D on alt ports only
$ ./target/release/httpjet --root /usr/local/lsws serve \
    --http-addr  127.0.0.1:8080 \
    --https-addr 127.0.0.1:4443 \
    --no-mtls \
    --php-socket   /tmp/php8-test.sock \
    --php-children 4 \
    --page-cache
!
Never the prod socket

A development serve uses a throwaway --php-socket (e.g. /tmp/php8-test.sock) and a low --php-children — never the production /tmp/php8-httpjet-c1.sock. --no-mtls relaxes the Cloudflare client-cert check for local TLS; loopback is exempt anyway. Benchmark only release or PGO builds — a debug build is several times slower and tells you nothing.
