Protocol stacks

httpjet speaks HTTP/1.1, a from-scratch native HTTP/2 stack, and HTTP/3 over QUIC through one unconditional io_uring / monoio transport layer. TCP and QUIC converge behind one unified rustls TLS configuration with optional client-certificate verification, and every protocol hands requests to the same request pipeline.

Overview

The transport paths now live in the binary's uring/ module. HTTP/1.1 is a custom monoio + httparse codec; HTTP/2 and cleartext h2c use httpjet's native hj-h2 stack through its monoio serve path; HTTP/3 is driven by uring/h3.rs, a quinn-proto QUIC loop with quinn-udp socket state over io_uring UDP. hj-http remains in the workspace as shared ServeConfig connection tuning, not as a transport adapter crate.

Protocol selection happens at the connection boundary. Over TLS it is ALPN: the negotiated token (h2 or http/1.1) picks the TCP stack, while QUIC connections use the HTTP/3 path. In cleartext, a non-destructive preface sniff detects an HTTP/2 prior-knowledge client and routes it to the native h2 stack; everything else is HTTP/1.1. Whichever protocol wins, the request is bridged into the same request pipeline and returns to the monoio core for framing and writes.

HTTP/1.1 & h2c detection

HTTP/1.1 is served by a custom monoio codec in the io_uring transport. It parses with httparse, enforces strict request framing, supports keep-alive and pipelining, honors LiteSpeed's maxKeepAliveReq cap (0 = unlimited), decodes chunked bodies, and streams large or long-lived responses back from the shared pipeline without buffering the whole body.

Cleartext HTTP/2 (h2c) by prior knowledge has no upgrade handshake — the client just sends the connection preface. httpjet detects it non-destructively while the bytes remain available to the selected stack. If the preface matches, those leading bytes are handed to the native h2 path; if not, the same unread bytes flow into the HTTP/1.1 parser. No replay buffer, no lost bytes.

uring · ALPN + cleartext routing
// over TLS: ALPN decides the TCP stack
match alpn {
    b"h2"       => hj_h2::server::serve_local_with_prefix(io, prefix, service, cfg).await,
    b"http/1.1" => handle_h1_bridged(io, prefix, service).await,
    _          => handle_h1_bridged(io, prefix, service).await,
}

// cleartext: sniff the preface and pass the bytes to the chosen stack
match sniff_cleartext(&mut stream).await? {
    Proto::Http2(prefix) => hj_h2::server::serve_local_with_prefix(stream, prefix, service, cfg).await,
    Proto::Http1(prefix) => handle_h1_bridged(stream, prefix, service).await,
};
i
Why the prefix matters

The h2c detector must not consume bytes invisibly. The selected stack receives exactly the prefix already observed plus the rest of the stream, so h1 and h2 both parse the connection as if no router sat in front of them.

Native HTTP/2

hj-h2 is httpjet's own HTTP/2 server. It serves every h2 connection the server takes: ALPN h2-over-TLS and cleartext h2c both land here through the monoio local serve path. The design is built around the Cloudflare→origin shape — a small number of long-lived connections each carrying many concurrent streams — so it optimizes for multiplexing one connection cheaply rather than spreading work over many connections.

  • One task per connection. A single local task multiplexes all streams on the connection via FuturesUnordered — there is no per-stream spawn on the hot path, so a 100-stream connection costs one task, not a hundred.
  • Send-side flow control. The server honors per-stream and connection windows on egress, pacing body writes to the peer's advertised capacity.
  • Streaming bodies. PHP/LSAPI, reverse-proxy, and SSE responses stream through without buffering, alongside async file streaming for static content.
  • One vectored write per wake. The task coalesces ready frames into a single vectored write each time it wakes; large bodies are zero-copy straight from page-cache Bytes.
  • Inbound RFC 9113 validation. Frames are validated on the way in, with a graceful GOAWAY drain on shutdown so in-flight streams finish.
  • Shared pipeline bridge. Stream dispatch uses the same bridge as h1 and h3, so rewrite, LSAPI, proxying, cache lookup, metrics, and reload state are identical across protocols.

Because handlers behind every protocol are the same closure, HTTP/2 does not have a separate backend path: a busy h2 connection exercises the same request pipeline as HTTP/1.1 and HTTP/3, then returns framed bytes to the monoio writer.

HPACK

HTTP/2 header compression is HPACK (RFC 7541), and httpjet's codec is the hpack submodule of hj-h2 — once a standalone crate, now folded in so it lives next to the only code that uses it. It is zero-allocation: header fields are decoded and encoded by slicing frame bytes in place rather than copying into intermediate buffers.

That in-place slicing is where hj-h2's unsafe lives — bounded bitwise indexing into the frame buffer, with the safety invariant documented above each block. HPACK's static and dynamic tables and the integer/string primitives all operate over borrowed frame slices, so a header block carries no per-field allocation on the hot path.

i
Where it lives

HPACK is not a separate dependency — it is hj-h2::hpack. Keeping the codec inside the h2 crate means the frame layout it slices and the connection state that drives it evolve together, with no cross-crate API to version.

HTTP/3 & QUIC

HTTP/3 is implemented in crates/httpjet/src/uring/h3.rs. It uses quinn-proto for QUIC state, quinn-udp for UDP socket metadata/GSO/GRO handling, drives UDP from monoio/io_uring, decodes and encodes QPACK, and dispatches requests through the same bridge used by H1 and H2. The H3 path currently collects the response body before encoding it; H1 and H2 stream large and SSE bodies incrementally.

Discovery is via Alt-Svc: TLS responses advertise the HTTP/3 endpoint, so an HTTP/2 client that connected over TCP learns it can upgrade to QUIC for subsequent requests. The advertisement is emitted on TLS responses as the last response transform, after the body is finalized.

One TLS config, two transports

TCP and QUIC do not maintain separate certificate stores or verifiers. build_server_config_alpn produces the rustls config used by the TCP path and by the QUIC crypto setup. A cert rotation or mTLS change lands in both at once.

TLS & mutual TLS

hj-tls builds one rustls::ServerConfig for TCP and QUIC via build_server_config_alpn(cfg, listener, alpn). The installed crypto provider is aws-lc-rs, and key parsing, TCP TLS, and QUIC setup all use that provider. Two pieces make up the config: how a certificate is selected per connection, and how (and whether) the client is verified.

Certificate selection is a custom SniCertMap resolver with no cert-name-match, mirroring OpenLiteSpeed: the SNI hostname maps directly to configured certificate material without re-validating that the chosen leaf's subject/SAN matches the SNI. The resolver is shared by both transports through the single config.

Client verification is optional mutual TLS. A WebPkiClientVerifier is attached to the listener CA when the native listener requests it; configured exempt IPs are a separate policy. A proxy-specific profile may supply trusted ranges and request metadata, but TLS verification itself is not tied to a provider.

hj-tls · one config, SNI + mTLS
fn build_server_config_alpn(cfg, listener, alpn) -> rustls::ServerConfig {
    // SNI → cert, NO cert-name-match (mirrors OpenLiteSpeed)
    let resolver = SniCertMap::from(cfg, listener);

    // optional mTLS: client verifier on the LISTENER CA only.
    let verifier = WebPkiClientVerifier::builder(listener.ca).build();

    rustls::ServerConfig::builder()
        .with_client_cert_verifier(verifier)
        .with_cert_resolver(resolver)
        .alpn(alpn)            // shared by TCP and QUIC
}
!
Load-bearing distinction

A per-vhost certificate chain is server chain material — intermediates the server presents to the client — not a client-verify root. Only the listener CA is the client verifier. httpjet keeps these roles strictly separate.

The zero-copy Bytes the h2 stack writes for large bodies come straight from the origin page cache, and the PHP/LSAPI streaming bodies these transports carry originate in the LSAPI & PHP backend.
