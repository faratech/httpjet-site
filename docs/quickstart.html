Quickstart

httpjet reads an existing LiteSpeed configuration as-is, so there's nothing to port. This walks from a clean checkout to a running origin you can curl — building the binary, linting the config, and serving on alternate ports with the page cache on. For a real deployment, see Operations; for every flag, see Configuration.

Prerequisites

  • A LiteSpeed configuration tree at /usr/local/lsws — conf/httpd_config.xml plus conf/vhosts/*.xml. httpjet consumes the same files LiteSpeed does; you point it at the root and it resolves listeners, vhosts, document roots, and ext-processors from there.
  • The lsphp binary (the LiteSpeed PHP SAPI) for any PHP vhost — httpjet speaks native LSAPI to it. PHP is optional: with --no-php, PHP requests fall back to static serving.
  • Rust 1.96 (edition 2021) and a C toolchain (the crypto + allocator crates build native code).
i
No migration

The same config file boots either server, so adopting httpjet is a cutover, not a port — and rolling back is one restart away. You do not rewrite anything to try it.

Build the binary

A debug build is fine for trying things out; a release build (LTO + a single codegen unit) is what you measure against, and the PGO build is what production runs.

build · cargo
# debug build — fast to compile, ~5x slower at runtime
cargo build

# release build (REQUIRED for any benchmarking)
cargo build --release          # → target/release/httpjet

# production build: profile-guided optimization (per architecture)
scripts/build-pgo.sh

The workspace is large (1 binary + 14 hj-* libraries), so when iterating on one crate, scope the build and tests with -p, e.g. cargo test -p hj-rewrite.

Lint the config

Before binding any port, dry-run the configuration. check parses the whole tree — variable substitution, listeners, vhost resolution — and prints errors and warnings without serving.

check · config lint
./target/debug/httpjet --root /usr/local/lsws check

Run it — for development

Serve on alternate ports with a separate lsphp socket and the page cache enabled. --no-mtls relaxes the Cloudflare client-certificate check for local TLS (loopback is exempt anyway), and a low --php-children keeps the worker count sane on a dev box.

serve · dev (alt ports)
./target/release/httpjet --root /usr/local/lsws serve \
    --http-addr  127.0.0.1:8080 \
    --https-addr 127.0.0.1:4443 \
    --no-mtls \
    --php-socket   /tmp/php8-httpjet-test.sock \
    --php-children 4 \
    --page-cache
!
Never touch the live edge

In production httpjet runs on :80/:443 behind Cloudflare. Always test on alternate ports with a separate --php-socket — never the production socket — so a test instance can't share the port (via SO_REUSEPORT) or the PHP pool with the live server.

Verify

Request a page twice and watch the X-LiteSpeed-Cache response header: the first cacheable request is a miss (it ran and stored), the second is a hit (served from cache, no PHP). An absent header means the response wasn't marked cacheable by the app.

verify · curl
# -k: accept the self-signed dev cert; -H: pick the vhost by Host
curl -skI -H 'Host: example.com' https://127.0.0.1:4443/ | grep -i x-litespeed-cache
# x-litespeed-cache: miss   (first request)
# x-litespeed-cache: hit    (second request — served from cache)
