Rewrite engine

hj-rewrite is httpjet's Apache mod_rewrite / .htaccess engine. It is one of three deliberately isolated crates — it takes no hj-* dependencies, so the rewrite semantics stay portable. It uses fancy-regex, not the regex crate, because real .htaccess files use negative lookahead — which the linear regex engine can't express.

Overview

The rewrite stage runs the inline <rewrite> rules first, then the .htaccess chain for the resolved directory — mirroring OpenLiteSpeed's dispatch order. The whole engine lives behind one entry point, evaluate(), which returns exactly one outcome per request: Rewritten, Redirect, Proxy, Forbidden, Gone, or Unchanged. Because the crate is dependency-isolated from the rest of the workspace, its match semantics can be reasoned about — and ported — on their own.

Per-directory loading

An HtaccessCache loads each directory's .htaccess with mtime invalidation — a changed file is reparsed on its next access. In production the config tree is read-only, so in practice each file is parsed once and then served from the cache for the life of the process. The parsed form holds the directive list, the compiled regexes, and the scoping blocks ready to evaluate.

evaluate() walks that parsed form once and produces a single outcome. There is no re-entrant re-evaluation per directive: a terminal flag ([L], a redirect, a forbid, a proxy hand-off) stops the walk, and an exhausted chain returns Unchanged so dispatch falls through to suffix routing.

The dense-DFA prefilter

The hot-path optimization. Rather than test every rule's regex on every request, the eligible rule patterns are compiled once into one fully-determinized dense DFA (regex_automata::dfa::dense) and searched a single time per request to learn which rules could possibly match. Only the rules the prefilter flags are then evaluated for real.

The reason it is a dense (fully-determinized) DFA and not the usual lazy one is contention: a fully-determinized DFA holds no lazy transition state, so the search is cacheless — there is no per-search Cache to allocate and no cross-thread Pool to lock. At high concurrency that removes a mutex from the request path entirely.

hot path · prefilter then evaluate
// one determinized DFA over all eligible patterns — no Cache, no Pool
let hits = prefilter.search(path);   // which rules *could* match
for rule in hits {
    if let Some(m) = rule.regex.find(path) {
        return rule.apply(m);     // substitute + flags
    }
}
return Outcome::Unchanged;

Linear vs backtracking matching

A rule the prefilter flags runs its pattern through a CompiledRegex that prefers the linear-time engine — regex_automata::meta::Regex, driven with an explicit thread-local Cache keyed per pattern so it sidesteps the high-level API's cross-thread mutex slow path. It falls back to fancy-regex only for the patterns the linear engine cannot express: lookaround (?=…)/(?!…) and in-pattern backreferences \1.

This split is safe because it is not a behavioral approximation. A pattern the linear engine accepts has identical match semantics under both engines, so choosing the linear path for it is transparent — the result is the same captures, the same boundaries, just without the backtracking cost. Only genuinely backtracking constructs ever reach fancy-regex.

Ordinary anchors, classes, alternationregex_automata::metaLinear time; per-pattern thread-local Cache, no shared pool lock.

SetEnvIf & lazy headers

SetEnvIf / SetEnvIfNoCase rules are evaluated with lazy header access: the engine hands the rule a callback that only materializes the HTTP headers if that rule actually references one. A request that matches no SetEnvIf rule therefore pays no header-materialization allocation at all — the common case stays free.

The attribute compare is case-insensitive without allocating a lowercased copy of either side, so even a matching rule avoids the obvious per-request String churn.

.htaccess · SetEnvIf with lazy access
SetEnvIfNoCase User-Agent "bot|crawler" is_bot=1
SetEnvIf Request_URI "\.(?:png|jpg|css|js)$" is_asset=1
# headers are only read if a rule above references them

Front-controller routing

This is the load-bearing correctness rule. XenForo's front controller rewrites every page to /index.php. If the engine let that rewrite overwrite the request identity, every distinct URL would look like /index.php to everything downstream.

So the engine keeps the original REQUEST_URI even after a rewrite to index.php — the resolved script path is pinned separately (it becomes SCRIPT_FILENAME, with SCRIPT_NAME/QUERY_STRING pushed into the request env). PHP sees the front controller; the rest of the pipeline still sees the real URL the visitor asked for.

!
Why the cache keys by the original URI

Because the rewrite to index.php preserves the original REQUEST_URI, the page cache must key by that original URI, never the rewrite-resolved path. Keying by the resolved path would collapse every page on the site to a single cache entry — and serve the wrong page to everyone after the first.

Access control

The engine also enforces .htaccess access control: <Files> / <FilesMatch> / <Directory> / <DirectoryMatch> / <If> scoping carrying allow / deny / Require, ANDed across every enclosing block. A request is permitted only if it survives all the blocks it falls inside.

A <Directory> deny applies to the directory and everything beneath it — a file inside a denied directory is denied even when its own path doesn't match the directory regex, so you can't tunnel under a block with a deeper path. Matchers fail closed toward the rule's polarity: if a deny pattern errors at match time it counts as matched (the deny still applies), and an allow that errors is withheld. A regex failure can therefore only ever make access more restrictive, never less.

i
Fail-closed, both directions

The polarity rule is the whole point: a deny that can't evaluate is treated as a deny, and an allow that can't evaluate is treated as absent. Either way the safe outcome is the restrictive one.

Ground truth

The GPL OpenLiteSpeed source was the reference for the exact flag and dispatch semantics — behavior was extracted and reimplemented cleanly. httpjet is MIT/Apache and never copies GPL code.

Performance & honesty

The engine's hot path is at its allocation floor: the cacheless dense-DFA prefilter, the per-thread regex caches, and stack-allocated capture arrays leave little left to shave. The remaining gap on one synthetic workload is structural, not an allocation problem.

⎁
Measured

On the heavy-.htaccess synthetic workload, LiteSpeed was historically far ahead — because httpjet runs the full uncacheable .htaccess pipeline on every request, including static files, where LiteSpeed short-circuits. Micro-optimizing the engine doesn't close it; the real lever for that workload is the page cache, which removes the pipeline from the hot path entirely.
