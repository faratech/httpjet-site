Performance

httpjet is fast — but these docs are unusually honest about where the time goes. Every number on this page names its regime, because a loopback benchmark (synthetic, on-box, PGO build) is not the same thing as production telemetry (real Cloudflare-fronted traffic). The short version: on a CF-fronted PHP site, almost all the wall time is in PHP, and httpjet's own CPU is a rounding error.

The honest framing

It is easy to publish a single impressive requests-per-second number and let the reader assume it describes their workload. It usually doesn't. A measurement only means something paired with the conditions that produced it, so this page attaches one of three regimes to every figure:

loopback benchmark · synthetic, on-box, PGO production telemetry · real CF-fronted traffic hardware counters · perf at saturation

A loopback benchmark removes the network, the TLS handshake cost of real clients, and Cloudflare entirely — it isolates the server's own code path, which is exactly what you want when comparing two servers, and exactly what you must not generalize to end-user latency. Production telemetry is the opposite: it measures what users actually feel, dominated by the backend and the edge. Both are below; neither is wrong; they answer different questions.

i
Read the regime, not just the number

The same server can show ~44.8k req/s on loopback and contribute ~0.2% of user-visible latency in production. Those are not in tension — the first measures httpjet in isolation, the second measures httpjet as one thin layer in a PHP-and-Cloudflare stack. Most "is it fast?" questions are really asking one or the other.

The codegen tier — PGO + mimalloc

Historical campaign binaries combined Profile-Guided Optimization (PGO), the mimalloc global allocator, and architecture-specific code generation. Those numbers are not portable release-binary promises. When comparing a change, build both sides with equivalent profiles and record the hardware, workload, cache state, and compiler settings.

The checked-in PGO flow is the classic three-step: build an instrumented binary, drive a representative loopback workload, then merge the profile and rebuild optimized. Its workload and CPU tuning belong to one deployment; adapt it or provide an equivalent neutral harness before using it elsewhere.

scripts/build-pgo.sh · instrument → gather → optimize
# 1. build an instrumented binary, 2. drive a representative loopback
#    workload (h2 cache-HITs dominant, plus h2/h1 static + PHP),
# 3. merge the profile and rebuild optimized.
$ scripts/build-pgo.sh

# Profiles and CPU tuning are architecture-specific. Build a neutral
# release artifact separately from any deployment-specific PGO workflow.

Because the profile is captured by running the instrumented binary, PGO is per-architecture: a binary only carries a profile gathered on its own instruction set, so any multi-arch release must build each target natively (the retired cross-build helpers are gone from the tree).

!
A non-PGO benchmark is not a benchmark

Debug builds are roughly 5× slower and meaningless for comparison, but even a plain release build differs from PGO by enough that a regression hunt can chase a phantom. When A/B-testing a change, build both sides the same way (both PGO, or both plain release) and interleave them — mixing a PGO binary against a non-PGO one fakes a ~10% delta out of pure binary layout.

Loopback throughput

These are isolated, on-box figures with the network and Cloudflare removed — the right comparison for "how fast is the server itself," and the wrong one for end-user latency. The primary dataset is the August 2026 dedicated-host three-way (httpjet vs OpenLiteSpeed vs nginx on a quiet box); the earlier June PGO campaign against a commercial-LiteSpeed baseline is kept as the PHP-path reference.

Measured

The August 2026 dedicated-host three-way run (quiet box, httpjet vs OpenLiteSpeed vs nginx): HTTP/2 empty bodies at c=50 do ~908k requests/s vs OpenLiteSpeed's ~793k (best pair; the second pair is a statistical tie), 1 KB bodies at c=200 are ~804k vs ~790k, and HTTP/1.1 empty at c=1000 is ~202k vs ~183k. nginx's h2 could not complete the low-concurrency cells in this harness.

The page cache remains the bigger lever for cacheable traffic, but uncached heavy-rewrite static is no longer an axis where LiteSpeed-family servers lead.

The origin cache result

The single largest performance fact about the real workload is not a server micro-optimization — it is the origin page cache. For the cacheable fraction of forum traffic, serving from the in-memory cache replaces an entire PHP render with a memory copy.

⎁
Measured

A cacheable guest pageview over HTTPS loopback: the cache HIT serves the 152 KB page from memory at 19,912 requests/s (p50 2 ms, p99 5 ms), while the same URL forced through the full DB-backed PHP render manages 196 requests/s (p50 93 ms) — ≈101× the throughput, ≈46× lower latency. (A static robots.txt reference run: 83.8k RPS.) The cache dominates the real CF-fronted forum workload precisely because it removes the backend from the request entirely.

loopback benchmark · PGO build · memory tier

A 2026-08-30 refresh under shared-box conditions (live production on the same host — directional only, absolutes several times lower by construction) put cache-hit serves at ~5.4k req/s h2 and ~6.7k h1 on real /help/* pages, in line with the preceding days' rows. The production hit ratio also reads low for a structural reason: ~51% of origin GET-200s are one-shot bot crawls whose repeat interval exceeds any TTL, so no cache tier can absorb them — the actionable lever there is edge TTL, not the origin cache. The cache's design, admission policy, and LSCache-compatible X-LiteSpeed-* protocol are covered under Page cache.

Where the time actually goes

The loopback numbers above isolate the server. Production telemetry answers the different, more important question: of the time a user waits, how much is httpjet? The answer came out of a layered diagnostic that walked from production attribution down through on-CPU profiling per regime, off-CPU syscall analysis, concurrency scaling, and finally hardware counters. The headline result is blunt.

⎁
Measured

In production, the lsphp / PHP render is 86.5–98.8% of total request wall time, measured across millions of requests on both nodes. httpjet's own CPU is about 0.2% of request latency — roughly 138 µs per request, or ~38 µs of CPU per cache HIT, and that 38 µs already includes TLS, HTTP/2, rewrite, the cache lookup, and access logging.

production telemetry · both nodes · millions of requests

A 2026-08-30 live sample pins the same conclusion with per-stage numbers: the mean request is 9.99 ms, of which 8.96 ms (90%) is LSAPI TTFB inside PHP (the pool-acquire itself is p99.9 < 1 ms), while the rewrite stage costs 5.4 µs and the cache lookup 3.2 µs — together 0.09% of the request. µs-shaving the serving path is arithmetically exhausted; the levers are the cache offload ratio and TLS resumption.

Put plainly: httpjet-side CPU is effectively invisible to users. The real levers for end-user latency are PHP and opcache speed and the cache hit ratio — not micro-optimizing a 0.2% share. The team chased the httpjet hot path to its floor (see below) and concluded exactly this: there is no meaningful user-facing win left in the server's own CPU, so the work that moves the needle lives in PHP / LSAPI speed and in cache hit-ratio and bypass behavior.

i
Why this changes the priorities

If httpjet is 0.2% of latency, halving its CPU would shave ~0.1% off the page — imperceptible. Conversely, turning a PHP render into a cache hit removes the other ~99%. That asymmetry is why the project stopped optimizing the server's CPU and instead invested in the cache, in PHP/opcache tuning, and in raising the cacheable fraction.

At the instruction floor

Before concluding that the server's CPU was a dead end, the team confirmed the HTTP/2 cache-HIT path was genuinely at its limit rather than merely slow. Two complementary measurements settled it.

⎁
Measured

At saturation the h2 cache-HIT path shows IPC 1.55, a 0.31% branch-miss rate, and 1.6 L1d misses per 100 instructions. Execution is efficient — the bottleneck is the number of instructions retired per request, not memory locality. The only CPU lever left is doing less work per request, not improving cache behavior.

hardware counters · perf at saturation

The second measurement cleared up a red herring. Syscall profiling showed futex traffic accounting for ~85% of syscall time, which superficially looks like lock contention — the kind of thing that caps throughput.

⎁
Measured

That futex traffic is idle parking and cross-thread waker churn, not lock contention. At the apparent ceiling the box was about 50% idle — the threads were waiting on work, not fighting over a lock. There was no contention bottleneck to remove.

strace / off-CPU analysis

Together these say the same thing from two directions: the hit path is instruction-bound and already efficient, and what looked like a concurrency wall was idle parking. There is no locality win and no contention win waiting to be found here.

Concurrency scaling

A natural worry with single-task-per-connection HTTP/2 multiplexing is that one connection becomes a ceiling. It doesn't. On the dedicated August run a single h2 connection sustained roughly 58k req/s (1 KB bodies), and throughput keeps rising with concurrency instead of collapsing:

The takeaway mirrors the rest of the page: measure carefully, name the regime, and check the harness before blaming the server. The corrected harness changed the HTTP/2 static story from a deficit into a lead; the heavy rewrite path remains the honest exception.

i
The plain takeaway

For a Cloudflare-fronted PHP site, the performance work that moves the needle is PHP speed and cache hit-ratio / bypass — not micro-optimizing httpjet's already-tiny CPU share. The hot path has been chased to its instruction floor and the conclusion is settled. Deployment and tuning of these levers live under Operations.
