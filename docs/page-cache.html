The origin page cache

An opt-in full-response origin cache. A cache hit returns the application-marked response without touching its backend. Native applications use X-HttpJet-* headers; a LiteSpeed compatibility profile can enable legacy aliases during a migration.

Overview

For cacheable application responses, the cache replaces an expensive render or upstream round trip with a memory or file-tier serve. It is disabled by default and should be enabled only after application-specific correctness checks.

Two crates split the work. The transport-agnostic store is hj-pagecache — a sharded page store with byte-weighted LRU eviction, tag/vary indexes, TTLs, and native cache protocol support. Store admission is separate: the binary's lscache glue records cacheable lookups in a fixed-memory frequency sketch and only stores keys that show reuse. cache_lookup runs before any backend; cache_store runs after terminal responses. The apparatus is inert when runtime.page_cache.enabled is false. See the request pipeline for the seams.

Opt-in by the app

The cache never guesses. A response is cached only when the application explicitly opts it in with X-HttpJet-Cache-Control. With no accepted cache-control header, the response is not cached. A page goes public with public,max-age=N; a configured session-keyed tier can accept private,max-age=N.

app → httpjet · the cache control header
// public page, cacheable for an hour
X-HttpJet-Cache-Control: public,max-age=3600

// per-session page (private tier)
X-HttpJet-Cache-Control: private,max-age=120

// drop every entry carrying this tag
X-HttpJet-Purge: tag=article-1234
i
Default is off

The cache is opt-in twice over: runtime.page_cache.enabled must be true and the application must emit an accepted cache-control header. There is no implicit caching or heuristic freshness.

The in-RAM index & admission

The index is a sharded in-RAM page store bounded by runtime.page_cache.memory_bytes (default 128 MiB). Entries are charged for resident metadata, standard variants, and any body bytes still in RAM; with a file tier on, file-backed bodies are charged metadata-only against this budget. Eviction is byte-weighted LRU inside the store's shards, so large resident entries cost proportionally more of the budget.

Admission uses a fixed-memory frequency sketch governed by runtime.page_cache.admission_threshold (default 2). An entry must clear a reuse bar before it is allowed to occupy the store — at the default, a URL is stored on its second sighting, so the third request is the first possible hit. Size-weighting raises the bar further for large bodies. A flood of unique URLs cannot evict the working set, because none earns admission in the first place.

Correctness invariants

A page cache that occasionally serves the wrong page is worse than no cache. Two invariants were learned the hard way and are now non-negotiable — each is enforced in code with a regression test.

!
Invariant 1 · key by the original URI

The entry key is the original request URI (orig_path / orig_query), never the rewrite-resolved path. XenForo's front controller rewrites every page to /index.php — so keying by the resolved path would collapse the entire site to one entry and serve the wrong page to everyone. The cache must read the URL the visitor asked for, not the script the rewrite landed on.

!
Invariant 2 · the identity guard

Every entry records the host + raw request-path it was built for, and a lookup serves a hit only if both match. A hash-key collision therefore degrades to a miss — it can never serve content built for a different URL. The guard makes "wrong content" structurally impossible, not merely improbable: the worst case is an unnecessary backend round-trip.

Vary, cookies & the private tier

Public entries may vary on explicitly configured cookie values. Before a public response is stored, Set-Cookie and both cache-header families are stripped from the stored copy — a public entry must never replay another visitor's session state. Applications should mark personalized routes uncacheable unless they deliberately use the private tier.

The private (per-session) tier is explicit policy, not authentication. A request carrying the configured logged-in marker cookie routes to a session-keyed private entry and never reads public entries; the application remains the authentication authority. The app opts the response in with X-HttpJet-Cache-Control: private,max-age=N.

Tag purge & cross-node coherence

Invalidation is tag-based rather than per-URL. When the app mutates content it emits X-HttpJet-Purge: tag=name, and every entry carrying that tag is dropped. A wildcard (*) purges everything. The compatibility profile can enable the legacy LiteSpeed alias.

In a cluster, purges fan out to configured peers. Required peer mode uses two independent controls: the raw source IP must be configured and the request must carry a fresh HMAC-SHA256 signature. File-tier purges unlink body files eagerly and retain a purge-all stamp so old data cannot be resurrected on a service restart.

purge · loopback / peer-gated endpoint
# tag purge (also fans out when cluster peers are configured)
curl -s -X POST -H 'x-httpjet-purge: tag=article-1234' http://127.0.0.1/__hj_cache_purge

# purge everything
curl -s -X POST -H 'x-httpjet-purge: *' http://127.0.0.1/__hj_cache_purge
i
Peer authentication

Loopback operations are local. Non-loopback peer purges in required mode must satisfy both the configured source-IP allow-list and HMAC authentication; peer authorization never creates a TLS client-auth exemption.

The store path

This is the write side — what happens after a backend produces a cacheable response. At store time the response is written under the original-URI key together with its identity (host + raw path), tags, vary set, and TTL. Cache semantics retain canonical identity bytes; its internal memory or file representation may be dictionary-compressed. Standard egress encoding is negotiated per serve, so a stored response is never tied to the first client's Accept-Encoding.

The store path also refuses a known footgun. A self-redirect guard declines to store an app-marked-cacheable 3xx whose Location is the request's own URL. Hosts are normalized without the port, because an HTTP/2 Host value may carry :443 while a generated absolute location may not.

!
Identity semantics, standard egress

Internal dictionary compression never changes the standard gzip, brotli, zstd, or identity bytes sent to a client. A missing compatible dictionary fails closed to a cache miss, never undecodable output.

Internal compression

Stored bodies can be dict-compressed against a zstd dictionary. Configure a global fallback with runtime.page_cache.dictionary or a dedicated file per vhost with vhost_dictionaries; the latter is usually more effective because each site has different common markup. Compression is scheduled after store, outside the client response path. This is purely an internal storage optimization — served bytes stay standard zstd/br/gzip or identity. A dict_gen field ties each stored body to the dictionary generation that decodes it, so a mismatch degrades to a miss rather than risk serving undecodable bytes.

To avoid storing one copy per encoding, the cache keeps one best variant chosen by the request's Accept-Encoding, using server priority zstd > br > gzip. A client whose accepted set doesn't match the stored variant falls back to a per-serve compress of the identity form. The mechanics of the negotiation itself live in Compression.

i
Dictionary lifecycle

Dictionaries are optional and must be trained from representative public, logged-out content for one vhost. They can retain source fragments, so never train from private pages. Rotation requires a full service restart; SIGHUP retains the loaded dictionary registry.

The file tier

By default the cache is in-RAM only and flushes on restart. Set runtime.page_cache.store_path to a directory to offload bodies into self-describing files at birth, off the process heap. The directory may be tmpfs or durable storage. A background boot scan rebuilds the index after a service restart; a host reboot clears a tmpfs tier but not a durable filesystem.

The file tier runs a dual-cap budget. memory_bytes bounds the in-RAM index (file-backed bodies charge metadata-only there), while disk_memory_bytes bounds file footprint through a disk-weight LRU. A served hit bumps file recency; eviction tears the whole entry down through one path. hot_memory_bytes fronts the store so the hottest bodies serve zero-syscall while a cold hit reads the file.

Stale-if-error & single-flight

Two mechanisms keep the cache useful under load and under failure.

Stale-if-error. When the backend returns a 5xx for a cacheable public GET, the cache can serve a retained stale entry instead of the error page. App-declared windows are bounded by native stale-if-error policy, which can also provide a fallback window. The response is marked X-HttpJet-Cache: hit,stale-if-error and Cache-Status; compatibility aliases are optional.

Stale-while-revalidate. App-declared stale windows are bounded by native stale policy. Standard Cache-Control can opt explicitly selected vhosts into origin caching through runtime.page_cache.standard_vhosts.

Single-flight. Concurrent misses of the same key collapse onto a single leader via a Notify. A stampede of requests for an uncacheable-or-slow page therefore hits the backend once rather than all at once — the followers wait on the leader's result instead of each launching their own render. (Registering on the leader's Notify before the pre-wait lookup is what closed a lost-wakeup collapse that had serialized misses one-at-a-time under concurrency.)

Observing the cache

Native cache responses carry X-HttpJet-Cache and standard Cache-Status. Two curls against a loopback instance make the lifecycle visible — the first stores, the second hits:

observe · native cache headers
# first request: ran the backend, stored the result
$ curl -I -H 'Host: example.test' http://127.0.0.1:8080/ | grep -Ei 'x-httpjet-cache|cache-status'
X-HttpJet-Cache: miss

# second request: served from cache, no PHP touched
$ curl -I -H 'Host: example.test' http://127.0.0.1:8080/ | grep -Ei 'x-httpjet-cache|cache-status'
X-HttpJet-Cache: hit

hitServed from cache — the backend was not touched.

(absent)Not cached — the app didn't opt the page in.

For aggregate state, a normally loopback-only metrics listener exposes /cache-entries: total entries and bytes, per-URL-class counts, a top-N by size, and a health line of hits/misses/stores/purges plus file read/write error counters. Judge cache health by hit ratio, errors, and direct content checks—not a raw file count.
