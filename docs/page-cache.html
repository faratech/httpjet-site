The origin page cache

A full-response origin cache that memoizes the pages the application marks cacheable, so a cache hit serves in microseconds without ever touching PHP. It is the LSCache equivalent — driven by the very same X-LiteSpeed-* headers the application's XenForo add-on already emits — so it is a drop-in for LiteSpeed's LSCache, not a re-implementation the app has to be re-taught.

Overview

Rendering a forum page is the expensive part of serving it: the PHP backend dominates request latency, while httpjet's own CPU is a rounding error. The page cache attacks that directly — it captures a fully-rendered response once and replays it for subsequent matching requests, turning a multi-millisecond PHP render into a microsecond memory serve. It is the single largest lever on the real Cloudflare-fronted workload.

Two crates split the work. The transport-agnostic store is hj-pagecache — a bespoke sharded in-RAM page store with byte-weighted LRU eviction, tag/vary indexes, TTLs, and the X-LiteSpeed-* protocol. Store admission is separate: the binary's lscache glue records cacheable lookups in a fixed-memory frequency sketch and only stores keys that show reuse. The ReqCtx-aware seams that wire it into the request lifecycle are also in lscache: cache_lookup runs before any backend (a hit short-circuits dispatch entirely) and cache_store runs after each terminal return. The whole apparatus is inert and ~zero-cost when the --page-cache flag is off. See the request pipeline for where the two seams sit.

Opt-in by the app

The cache never guesses. A response is cached only when the application explicitly opts it in by emitting an X-LiteSpeed-Cache-Control response header — exactly the contract LSCache uses, which is why the existing XenForo add-on drives httpjet unchanged. With no such header, the response is not cached at all. A page goes public with public,max-age=N; logged-in pages opt into the private tier instead (see below).

app → httpjet · the cache control header
// public page, cacheable for an hour
X-LiteSpeed-Cache-Control: public,max-age=3600

// per-session page (private tier), TTL capped at 300s
X-LiteSpeed-Cache-Control: private,max-age=120

// drop every entry carrying this tag
X-LiteSpeed-Purge: tag=T1234
i
Default is off

The cache is opt-in twice over: it requires both the --page-cache runtime flag and an X-LiteSpeed-Cache-Control header on the response. Absent either, the path is a near-free pass-through — there is no implicit caching, no heuristic freshness, and no surprise on a page the app didn't bless.

The in-RAM index & admission

The index is a bespoke sharded in-RAM page store bounded by --page-cache-mem (default 128 MiB; live production currently uses a 4 GiB cap). Entries are charged for resident metadata, precompressed variants, and any body bytes still in RAM; with the file tier on, persisted body bytes move to the tmpfs body budget instead. Eviction is byte-weighted LRU inside the store's shards, so large resident entries cost proportionally more of the budget.

Admission uses a fixed-memory frequency sketch governed by --page-cache-admit-threshold (default 2). An entry must clear a reuse bar before it is allowed to occupy the store — at the default, a URL is stored on its second sighting, so the third request is the first possible hit. Size-weighting raises the bar further for large bodies. The net effect: a flood of unique URLs (a crawler, a scrape, a long-tail spike) cannot evict the working set, because none of those URLs ever earns admission in the first place.

Correctness invariants

A page cache that occasionally serves the wrong page is worse than no cache. Two invariants were learned the hard way and are now non-negotiable — each is enforced in code with a regression test.

!
Invariant 1 · key by the original URI

The entry key is the original request URI (orig_path / orig_query), never the rewrite-resolved path. XenForo's front controller rewrites every page to /index.php — so keying by the resolved path would collapse the entire site to one entry and serve the wrong page to everyone. The cache must read the URL the visitor asked for, not the script the rewrite landed on.

!
Invariant 2 · the identity guard

Every entry records the host + raw request-path it was built for, and a lookup serves a hit only if both match. A hash-key collision therefore degrades to a miss — it can never serve content built for a different URL. The guard makes "wrong content" structurally impossible, not merely improbable: the worst case is an unnecessary backend round-trip.

Vary, cookies & the private tier

Public entries vary on the public style/language cookie set, so a guest viewing the dark theme and a guest viewing the light theme get distinct variants rather than poisoning each other. Before a public response is stored, the Set-Cookie and X-LiteSpeed-* headers are stripped from the stored copy — a public entry must never hand one visitor's session cookie to the next. A logged-in request bypasses the public cache entirely via the .htaccess [E=no-cache] env, so a member's personalized page can never land in (or be served from) the shared public set.

The private (per-session) tier (--page-cache-private, live in production) is the one cache change with real upside for the logged-in fraction of traffic, which is otherwise structurally uncacheable. When the xf_user cookie is present, the request routes to a per-xf_session key and never touches the public entries in either direction. The app opts a page into it with X-LiteSpeed-Cache-Control: private,max-age=N; the private TTL is capped at 300 s so a member's view is short-lived by construction.

Tag purge & cross-node coherence

Invalidation is tag-based rather than per-URL. When the app mutates content it emits X-LiteSpeed-Purge: tag=T<id>, and every entry carrying that tag is dropped — so a single reply to a thread can evict the thread view, the forum index, and any digest that referenced it, without the app enumerating their URLs. A wildcard (*) purges everything.

Two properties make purge production-safe across the active-active pair. First, a purge fans out to the peer node (--cache-peer) so both origins stay coherent — an invalidation on one node is mirrored to the other rather than leaving a stale copy live behind Cloudflare. Second, when the file tier is on, purges are durable across a restart: the tmpfs files are unlinked eagerly and a purge-all stamp is written, so a restart can't resurrect a purged entry from disk.

purge · loopback / peer-gated endpoint
# tag purge (also fans out to the peer node)
curl -s -X POST -H 'x-litespeed-purge: tag=T1234' http://127.0.0.1/__hj_cache_purge

# purge everything
curl -s -X POST -H 'x-litespeed-purge: *' http://127.0.0.1/__hj_cache_purge
i
Peer-gated, not secret-gated

The purge endpoint is authorized by the raw TCP source IP being a configured --cache-peer or loopback (127.0.0.1/::1) — a narrow allow-list, no shared secret. A Cloudflare-relayed or direct-to-origin request presents a public peer IP and simply gets a 404.

The store path

This is the write side — what happens after a backend produces a cacheable response. At store time the response is written under the original-URI key together with its identity (host + raw path, for the guard), its tags, its vary set, and its TTL. Crucially the body is kept uncompressed: compression stays a per-serve decision, so a cache hit re-negotiates the client's Accept-Encoding at serve time rather than being pinned to whatever encoding the first requester happened to accept. One stored body satisfies a gzip client, a brotli client, and a zstd client alike.

The store path also refuses a known footgun. A self-redirect guard declines to store an app-marked-cacheable 3xx whose Location is the request's own URL — the homepage / → / loop class, where a cached redirect-to-self becomes an infinite bounce that Cloudflare then pins at its edge. The guard is checked at three layers (the add-on's own isSelfRedirect(), the store guard, and a serve-time re-check), and hosts are normalized port-agnostically because an HTTP/2 HTTP_HOST carries :443 while a board-URL Location is port-less.

!
Store uncompressed, serve compressed

Storing the identity body and compressing per-serve is what lets a single entry serve every encoding correctly. It is also why the internal dictionary compression (next section) is orthogonal: it shrinks the stored copy on the heap/tmpfs without changing the standard bytes that go out on the wire.

Internal compression

Stored bodies are optionally dict-compressed against a shared zstd dictionary (--page-cache-dict), which makes the stored copy roughly 3.5–9× smaller on the heap and on tmpfs. Production uses a shared dictionary with a RAM-only store path, so the working set remains tiny relative to the 4 GiB index cap. This is purely an internal storage optimization — the served bytes stay standard zstd/br/gzip, negotiated per request. A dict_gen field ties each stored body to the dictionary generation it was compressed with, so a lookup under a different or absent dictionary degrades to a miss rather than risk serving undecodable bytes.

To avoid storing one copy per encoding, the cache keeps one best variant chosen by the request's Accept-Encoding, using server priority zstd > br > gzip. A client whose accepted set doesn't match the stored variant falls back to a per-serve compress of the identity form. The mechanics of the negotiation itself live in Compression.

The tmpfs file tier

By default the cache is in-RAM only and flushes on restart. Point --page-cache-store-path at a directory (for example /dev/shm/jetcache) and it becomes tmpfs-primary — the LSWS-Enterprise model. store offloads every body to a self-describing tmpfs file at birth (off the process heap), a background task dict-recompresses each file in place, and the cache survives restarts and deploys via a background boot scan that rebuilds the index from the files on disk. A systemctl restart httpjet no longer cold-starts the cache.

The file tier runs a dual-cap budget. --page-cache-mem still bounds the in-RAM index (which now charges a persisted body as metadata-only, since its bytes live on tmpfs), while a separate --page-cache-disk-mem cap bounds tmpfs bodies via the store's disk-weight LRU list — a served hit bumps disk recency, and a disk eviction tears the whole entry down through one teardown path. A small --page-cache-hot-mem RAM tier fronts the store so the hottest bodies serve zero-syscall, while a cold hit pays one ~µs tmpfs read.

Stale-if-error & single-flight

Two mechanisms keep the cache useful under load and under failure.

Stale-if-error. When the backend returns a 5xx for a cacheable public GET — including the 503s an lsphp-down condition produces — the cache serves the retained stale entry instead of the error page, tagged X-LiteSpeed-Cache: hit,stale-if-error. App-declared windows are capped by --page-cache-stale-if-error-max-secs; --page-cache-stale-if-error-default-secs can apply a fallback window when the app declares none. The stale serve goes out with no-store egress so Cloudflare never pins it at its edge: visitors keep seeing the last good render while the backend recovers, and nothing downstream caches the degraded state.

Stale-while-revalidate. App-declared stale windows are capped by --page-cache-stale-max-secs, and --page-cache-stale-default-secs can provide a default when the app only gives a fresh lifetime. Standard Cache-Control can opt selected vhosts into origin caching through --page-cache-standard-vhosts; the production list is explicit rather than global.

Single-flight. Concurrent misses of the same key collapse onto a single leader via a Notify. A stampede of requests for an uncacheable-or-slow page therefore hits the backend once rather than all at once — the followers wait on the leader's result instead of each launching their own render. (Registering on the leader's Notify before the pre-wait lookup is what closed a lost-wakeup collapse that had serialized misses one-at-a-time under concurrency.)

Observing the cache

Every served response carries an X-LiteSpeed-Cache header that says exactly what happened. Two curls against a loopback instance make the lifecycle visible — the first stores, the second hits:

observe · the X-LiteSpeed-Cache header
# first request: ran the backend, stored the result
$ curl -skI -H 'Host: windowsforum.com' https://127.0.0.1/help/ | grep -i cache
X-LiteSpeed-Cache: miss

# second request: served from cache, no PHP touched
$ curl -skI -H 'Host: windowsforum.com' https://127.0.0.1/help/ | grep -i cache
X-LiteSpeed-Cache: hit
X-LiteSpeed-CacheMeaning
hitServed from cache — the backend was not touched.
missThe cache ran but didn't have the entry; the response was just stored.
hit,stale-if-errorBackend 5xx; the retained stale entry was served (no-store egress).
(absent)Not cached — the app didn't opt the page in.

For aggregate state, a loopback-only metrics listener exposes /cache-entries: total entries and bytes, per-URL-class counts, a top-N by size, and a health line of hits/misses/stores/purges plus the read/write error counters. It is the right gauge of cache health — judge by hit ratio and error counts, never by a raw on-disk file count, which can oscillate benignly as the tmpfs body LRU evicts cold entries.
