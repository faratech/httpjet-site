Conformance & standards

httpjet preserves LiteSpeed compatibility where an explicit migration profile requires it and targets standards conformance on the wire everywhere else. Prior differential testing reached 11/11 parity on the retained compatibility matrix; the native HTTP/2 stack passes 146 of 146 h2spec cases; and the protocol stacks track the current RFCs for HTTP/1.1, HTTP/2, HTTP/3, and TLS.

Overview

Two axes define httpjet's conformance posture. The first is LiteSpeed compatibility: XML migration, LSAPI, legacy ETags, cache aliases, and .htaccess behavior are retained where a selected compatibility profile needs them. The second is standards conformance: on the wire, httpjet must be a correct HTTP/1.1, HTTP/2, and HTTP/3 server for compliant clients and proxies.

Where the two agree, there is one right answer. Where LiteSpeed's behavior is a deliberate choice that a strict reading of the spec would call optional, httpjet matches LiteSpeed — the fileETag=28 format and the .html→PHP dispatch ordering are the clearest examples.

LiteSpeed parity

Prior differential conformance testing reached 11/11 parity against LiteSpeed on retained migration behaviors — ETag format, .html→PHP dispatch, LSAPI encoding, and rewrite flags. The differential apparatus is historical; new features belong in native TOML first and should be tested against their documented contract.

The authoritative reference for LiteSpeed's exact behavior was the GPL OpenLiteSpeed source. Behavior was extracted and reimplemented cleanly — httpjet is MIT/Apache and never copies GPL code.

i
Clean-room, not a fork

OpenLiteSpeed (GPL) was read only to learn the behavior — ETag formatting, the .html→PHP dispatch decision, LSAPI framing, rewrite flag semantics — which was then reimplemented from scratch. No GPL code lives in httpjet's MIT/Apache tree. The license boundary is deliberate and load-bearing.

HTTP/1.1

The HTTP/1.1 transport tracks RFC 9110 (HTTP semantics) and RFC 9111 (HTTP caching). That covers strict request framing, conditional requests (If-Modified-Since / If-None-Match), byte-range requests, and correct Vary handling so that cached and negotiated responses don't leak across representations.

These semantics are not just transport plumbing — they are what lets the static handler emit correct 304 Not Modified responses and what lets the page cache vary safely on the request's encoding and cookie set without serving the wrong representation.

HTTP/2 & HPACK

All HTTP/2 — both ALPN h2 over TLS and cleartext h2c — runs through httpjet's native hj-h2 stack. Inbound RFC 9113 validation is enforced on every frame, and the header codec is a from-scratch, zero-allocation RFC 7541 HPACK implementation.

The stack passes 146 of 146 h2spec conformance cases. Current hardening also covers no-forward-progress protections, strict connection and stream limits, and graceful GOAWAY drain behavior so bad clients fail closed without taking healthy streams with them.

HTTP/3 & QUIC

HTTP/3 follows RFC 9114 running over RFC 9000 (QUIC), with QPACK for header compression. The active implementation is the io_uring H3 driver in uring/h3.rs, using quinn-proto for QUIC state, quinn-udp for UDP socket metadata/GSO/GRO handling, and the same bridge into the request pipeline as H1/H2. The same unified rustls ServerConfig family backs TCP and QUIC, so SNI resolution, certificate selection, and the Cloudflare mTLS boundary behave identically across transports.

i
Current transport audit

The June 2026 transport pass tightened H1 conflicting length handling, chunked decoding, H2 progress/limit checks, H3 parser limits, loopback-only observability, IPv4-mapped ACL handling, symlink-owner failure behavior, and normalized directory redirects.

TLS & mTLS

The TLS layer is rustls with the aws-lc-rs crypto backend. In front of the origin, Cloudflare presents a client certificate that httpjet verifies with a WebPkiClientVerifier — the mutual-TLS trust boundary that fails closed for any peer that isn't Cloudflare (loopback is exempt, and the check can be relaxed for local TLS testing).

SNI resolution mirrors OpenLiteSpeed: the resolver maps the SNI name to a vhost certificate with no cert-name-match requirement, exactly as OLS does. A per-vhost <vhssl><CACertFile> is server chain material, not a client-verify root — only the listener CA is the client verifier, and those two roles are kept strictly distinct.

!
Distinct trust roots

Do not conflate the per-vhost CACertFile (server chain material sent to clients) with the listener CA (the root that verifies Cloudflare's client certificate). Treating the vhost chain CA as a client-verify root would silently widen the mTLS trust boundary.

ETag & dispatch fidelity

Static responses carry an ETag that matches LiteSpeed's fileETag=28 setting exactly:

fileETag=28 · byte-for-byte
// LiteSpeed fileETag=28: size, mtime, inode — three trailing semicolons
ETag: "<size>-<mtime>-<inode>;;;"

// e.g.
ETag: "4096-1718800000-1572934;;;"

The three trailing semicolons are not a typo — they are part of LiteSpeed's format, and a strict cache-validation client compares the ETag byte-for-byte. Drop a semicolon and conditional requests silently stop matching.

Suffix routing and the .html→PHP dispatch decision follow OpenLiteSpeed's ordering, including the source-disclosure guard: a script whose context has no PHP pool returns 503 and must never fall through to the static handler, which would otherwise serve the raw PHP source.

i
One fall-through is forbidden

A proxy context that can't resolve its ext-processor falls through to static — that's fine. A script with no PHP pool hard-fails 503 and is the one terminal that must never fall through. The distinction is the difference between a graceful degrade and disclosing source code.

Apache .htaccess

The rewrite engine reproduces Apache .htaccess behavior: mod_rewrite directive and flag semantics, access control (<Files> / <Directory> / <If> blocks and Require), Header, ErrorDocument, and SetEnvIf. Because real-world .htaccess files use negative lookahead, the engine is built on fancy-regex rather than the standard regex crate.

For the full directive coverage and the rewrite evaluation flow, see the Rewrite engine.

How it's tested

Conformance is held in place by roughly 1,050 tests across the 15 crates. They span three layers:

LayerWhat it covers
unitPure logic in each crate: config parsing, rewrite evaluation, HPACK encode/decode, ETag formatting, cache-key generation.
integrationCrate boundaries: loading real .htaccess files through the full rewrite engine, h2/h3 round-trips, full-pipeline dispatch tests.
live (#[ignore])Run individually with their documented prerequisites: explicit LiteSpeed fixtures, an LSAPI binary, capabilities, loopback ports, a backend, or a performance corpus. Do not run all ignored tests as one batch.

On top of the test suite, every deploy runs a set of cache-correctness regression gates that must pass before the cache ships to either node: front-controller cache-poisoning (three distinct URLs keep their own content), cross-scheme redirect loops (an HTTP-origin canonical 301 must not poison the HTTPS entry), foreign-host isolation, and private-tier session isolation. These gates, and the deploy flow they protect, are covered in Operations.
