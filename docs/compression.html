Compression

hj-compress encodes responses with three codecs — gzip, brotli, and zstd — chosen by server priority but always bounded by what the client's Accept-Encoding actually allows. Buffered bodies are encoded in one shot; streamed bodies stay streaming through a lazy per-chunk wrapper; and a trusted-proxy peer (Cloudflare) can be handed forced zstd egress to push the brotli cost off the origin.

Overview

Compression runs in the finalize stage of the pipeline, after a handler has produced a response and before it goes to the wire. It is a response transform: it inspects the negotiated codec, encodes the body, and sets Content-Encoding accordingly. The crate is self-contained — it carries the three codec backends and the negotiation logic, and it also provides the shared zstd dictionary that the page cache uses for internal storage dedup.

Codecs

Three codecs ship in hj-compress, each behind its own backend:

CodecBackendNotes
gzipflate2The universal fallback — every client accepts it.
brotlibrotliDense text encoding; broadly accepted by browsers.
zstdzstdCheapest to produce at comparable ratios; preferred when the client accepts it.

Server-priority negotiation

The server expresses a fixed preference — zstd > brotli > gzip — but it only ever picks a codec the client's Accept-Encoding actually allows. The negotiation walks the server's priority order and selects the first codec the client permits. So a modern client that accepts zstd is served zstd; a client that only accepts gzip is served gzip; a client that accepts nothing gets the body uncompressed.

Buffered vs streamed bodies

The encoding strategy depends on the body shape from hj-core:

  • A buffered body (Body::Full) is encoded in one shot via encode_bytes — the whole payload is already in memory, so the codec runs once over the full slice.
  • A streamed body (Body::Stream — proxy responses, SSE) is wrapped in a lazy per-chunk CompressStream. Each inbound chunk is encoded as it arrives, so the response stays streaming and is never aggregated or buffered. This keeps proxy and server-sent-event responses pass-through, with no latency penalty from collecting the whole body before sending the first byte.
i
Why it matters

Buffering a streamed body to compress it in one shot would defeat the point of streaming — SSE would stop being real-time and a slow proxy backend would hold the first byte hostage. CompressStream keeps the stream flowing while still compressing it.

Per-thread zstd contexts

zstd encoding uses a per-thread ZSTD_CCTX pool — a thread-local compress context that is reused across calls on the same worker thread. Allocating a fresh context per call would add an allocation to every compressed response; the thread-local pool amortizes that to roughly once per thread for the life of the process.

Trusted-proxy zstd egress

When httpjet sits behind a configured Cloudflare origin proxy, integrations.cloudflare.send_zstd = true can force zstd egress for that trusted peer, ignoring the forwarded Accept-Encoding. The proxy decodes that response and re-encodes for browsers. This integration is off by default and never applies to untrusted or direct clients.

forced zstd egress to a trusted proxy
# native TOML — only after trusted proxy ranges are configured

i
Trusted peers only

CF-zstd never affects untrusted or direct clients. A browser hitting the origin directly still gets only what its own Accept-Encoding asked for — the forced-zstd override applies strictly to the configured trusted-proxy peer.

Interaction with the page cache

The page cache stores one best variant per entry, chosen by the request's Accept-Encoding under the same server priority (zstd > br > gzip). A client whose acceptable encodings don't match the stored variant falls back to per-serve compression — the body is re-encoded on the way out. Either way the served bytes always stay standard zstd, brotli, or gzip.

The cache's internal dict compression is a storage optimization only: dictionaries can be configured per vhost, they never reach the wire, and a cached hit is decoded back to identity before standard client compression is selected.

Decode safety

Decoding is hardened against malformed input as defense-in-depth. The zstd decoder caps windowLogMax and bounds the decoded output size, so a hostile or corrupt frame can't coerce httpjet into an outsized allocation. A malformed frame fails the decode rather than ballooning memory.
